# Task 01: Schema Migration — Onboarding, Licences, Applications, Activation

## Status

complete

## Wave

1

## Description

This feature needs a substantial data-model addition: a driver's licence on file, a submitted application with per-document review state that survives resubmission, an activation flag that gates dispatch, and a handful of fields the design collects that the schema doesn't have yet (ID number, date of birth, colour, chassis body type, declared payload/dimensions). This task adds all of it to `prisma/schema.prisma` in one migration. Every other task in this feature depends on these tables/columns existing. It also extends the `GeorgianCity` enum with the 38 additional cities the design requires (the browser-side mirror of that enum is a separate task — `task-02` — since it's a different file with no schema dependency).

Read this task file in full before starting — several of the choices below (versioned documents instead of overwritten ones, a JSON draft blob instead of normalized in-progress columns, compliance-only payload overrides) are deliberate and explained inline; don't "simplify" them.

### 2. New enums

Place these near the existing `DriverAccountType`/`VehicleCategory` enums:

```prisma
/// Licence classes a driver may hold, gating which vehicle class they may
/// register during onboarding. B = cars/vans up to 3.5t, C = rigid trucks
/// over 3.5t, CE = truck with trailer / articulated.
enum LicenceCategory {
  B
  C
  CE
}

/// The physical body of a vehicle, collected during onboarding. Display and
/// compliance-review only — it does not participate in order matching or
/// pricing, both of which continue to key on `Vehicle.vehicleTypeSpecId`
/// alone. See the `driver-vehicle-onboarding` spec's vehicle-classes mapping
/// for how (class, chassis type) resolves to a specific `VehicleTypeSpec`.
enum ChassisType {
  DRY_BOX
  REFRIGERATED
  OPEN_CHASSIS
}

/// Lifecycle of one driver's onboarding application. `DRAFT` covers the whole
/// in-progress wizard (nothing has been reviewed yet); `PENDING` and
/// `ACTION_REQUIRED` can alternate any number of times as documents are
/// flagged and replaced; `APPROVED` is terminal for this feature (see
/// `requirements.md`'s Assumptions — there is no "rejected, start over" state).
enum DriverApplicationStatus {
  DRAFT
  PENDING
  ACTION_REQUIRED
  APPROVED
}

/// Which of the three documents an onboarding application collects.
enum DriverApplicationDocumentType {
  PROFILE_PHOTO
  LICENCE_FRONT
  LICENCE_BACK
}

/// Per-document review verdict.
enum DriverApplicationDocumentStatus {
  PENDING
  APPROVED
  FLAGGED
}
```

### 3. New `DriverLicence` model

One per driver, 1:1 on `DriverProfile`. No document paths here — both licence photos are `DriverApplicationDocument` rows (see below); this model only holds the licence's own facts, matching how `DriverProfile` itself holds identity facts. Place it directly after `DriverProfile` in the file:

```prisma
/// A driver's licence on file, collected during onboarding and written at
/// submit time (see `DriverApplication.draft`). 1:1 with `DriverProfile` — a
/// driver has exactly one current licence; a future renewal flow would
/// update this row in place, not create a new one. `categories` gates which
/// vehicle classes the driver may register.
model DriverLicence {
  id              String            @id @default(cuid())
  driverProfileId String            @unique
  driverProfile   DriverProfile     @relation(fields: [driverProfileId], references: [id], onDelete: Cascade)
  licenceNumber   String
  expiresAt       DateTime
  categories      LicenceCategory[]
  createdAt       DateTime          @default(now())
  updatedAt       DateTime          @updatedAt
}
```

### 4. New `DriverApplication` model

1:1 on `DriverProfile`. `draft` carries the whole in-progress wizard as a versioned JSON blob (`{ version: 1, personal: {...}, licence: {...}, vehicle: {...} }` — the exact shape is defined and parsed in `task-05`) so the wizard is resumable before anything is validated or written to normalized tables. `Vehicle` and `DriverLicence` rows are only created at a successful submit (`task-13`), inside one transaction — never from an intermediate draft save, because `Vehicle.plateNumber` is globally `@unique` and an abandoned draft must never be able to permanently claim a real plate. Place it directly after `DriverLicence`:

```prisma
/// One onboarding application per independent driver, 1:1 on `DriverProfile`.
/// `reference` is the short human-readable code shown to the driver and the
/// admin reviewer (e.g. "APP-40219") — a bare `cuid` isn't fit for that. Admin
/// review actions (approve/flag a document, request changes, approve the
/// driver) are recorded as `AuditLog` rows rather than a reviewer FK on this
/// model, matching how every other admin action in this codebase is audited.
model DriverApplication {
  id                String                       @id @default(cuid())
  driverProfileId   String                       @unique
  driverProfile     DriverProfile                @relation(fields: [driverProfileId], references: [id], onDelete: Cascade)
  reference         String                       @unique
  status            DriverApplicationStatus      @default(DRAFT)
  draft             Json?
  draftStep         Int                          @default(1)
  draftUpdatedAt    DateTime?
  // Set only once submit succeeds and the Vehicle row exists (SetNull, not
  // Cascade, so retiring a vehicle later never erases application history —
  // matches Order.vehicleId's existing onDelete choice).
  vehicleId         String?
  vehicle           Vehicle?                     @relation(fields: [vehicleId], references: [id], onDelete: SetNull)
  firstSubmittedAt  DateTime?
  lastSubmittedAt   DateTime?
  submissionCount   Int                          @default(0)
  documents         DriverApplicationDocument[]
  createdAt         DateTime                     @default(now())
  updatedAt         DateTime                     @updatedAt

  @@index([status])
}
```

### 5. New `DriverApplicationDocument` model

One row per uploaded document **per review round**, not one row overwritten forever — a retake inserts a new row (`task-06`) and sets `supersededAt` on the previous live row for that `(driverApplicationId, type)` pair, so an admin reviewing a resubmission can still see why the earlier photo was rejected instead of the rejection reason silently vanishing. Place it directly after `DriverApplication`:

```prisma
/// One row per uploaded onboarding document per review round. A retake
/// inserts a new row and supersedes the previous one rather than overwriting
/// it, so an earlier rejection reason stays visible to the reviewer. Exactly
/// one row per (driverApplicationId, type) has `supersededAt: null` — the
/// live one — enforced by a partial unique index added by hand below, the
/// same pattern `Vehicle.vehicle_single_owner_check` already uses for a
/// constraint Prisma's schema language can't express natively.
model DriverApplicationDocument {
  id                  String                           @id @default(cuid())
  driverApplicationId String
  driverApplication   DriverApplication                @relation(fields: [driverApplicationId], references: [id], onDelete: Cascade)
  type                DriverApplicationDocumentType
  storagePath         String
  status              DriverApplicationDocumentStatus  @default(PENDING)
  flagReason          String?
  supersededAt        DateTime?
  createdAt           DateTime                         @default(now())
  updatedAt           DateTime                         @updatedAt

  @@index([driverApplicationId])
}
```

### 7. New fields on `Vehicle`

Add `chassisType`, the declared-capacity overrides, and `colour` — all nullable, since every existing `Vehicle` row (company fleet, driver "add a vehicle") predates this feature and none of these are collected by those forms:

```prisma
model Vehicle {
  id                String                    @id @default(cuid())
  driverProfileId   String?
  driverProfile     DriverProfile?            @relation(fields: [driverProfileId], references: [id], onDelete: Cascade)
  companyId         String?
  company           LogisticsCompany?         @relation(fields: [companyId], references: [id], onDelete: Cascade)
  vehicleTypeSpecId String
  vehicleTypeSpec   VehicleTypeSpec           @relation(fields: [vehicleTypeSpecId], references: [id])
  plateNumber       String                    @unique
  make              String
  model             String
  year              Int
  colour            String?
  // Body type as collected during onboarding — display/compliance only, see
  // the ChassisType enum's own doc comment.
  chassisType       ChassisType?
  // Driver-declared overrides collected during onboarding, distinct from
  // vehicleTypeSpec's class-level values below them. These are attestations
  // for compliance review, never read by pricing or order matching — both
  // continue to use only vehicleTypeSpec's payload/dimensions, the single
  // source of truth for what a *class* of vehicle can carry. A submit-time
  // server check requires payloadKg to be at or above the resolved spec's
  // maxPayloadKg, so a vehicle can never be registered under a class it
  // physically can't meet.
  payloadKg         Float?
  cargoLengthM      Float?
  cargoWidthM       Float?
  cargoHeightM      Float?
  photoUrls         String[]
  orders             Order[]
  assignments        DriverVehicleAssignment[]
  driverApplications DriverApplication[]
  createdAt         DateTime                  @default(now())
  updatedAt         DateTime                  @updatedAt

  @@index([driverProfileId])
  @@index([companyId])
}
```

The model's existing doc comment currently reads *"Load capacity and cargo dimensions are not stored here — they come from `vehicleTypeSpec`, so there is a single source of truth per vehicle class."* Update it to stay true given the new columns — replace that sentence with:

```
/// Load capacity and cargo dimensions authoritative for pricing and order
/// matching come from `vehicleTypeSpec` — that remains the single source of
/// truth per vehicle class. `payloadKg`/`cargoLengthM`/`cargoWidthM`/
/// `cargoHeightM` below are separate, driver-declared overrides collected
/// during onboarding for compliance display only; nothing outside the
/// onboarding admin review reads them.
```

### 8. New fields on `DriverProfile`

Add `idNumber`, `dateOfBirth` (mirroring `ClientProfile`'s existing precedent for both), `profilePhotoPath` (private-bucket path, mirrored from the approved `DriverApplicationDocument` at approval time — not written at upload, to avoid drift if the photo is retaken), and `activatedAt`:

```prisma
model DriverProfile {
  id          String            @id @default(cuid())
  userId      String            @unique
  user        User              @relation(fields: [userId], references: [id], onDelete: Cascade)
  isOnline    Boolean           @default(false)
  city        GeorgianCity
  accountType DriverAccountType
  firstName   String?
  lastName    String?
  companyName String?
  vatId       String?
  phone       String
  idNumber    String?
  dateOfBirth DateTime?
  profilePhotoPath String?

  companyId String?
  company   LogisticsCompany? @relation(fields: [companyId], references: [id], onDelete: SetNull)

  // Set once an admin approves this driver's onboarding application (or, for
  // account types/paths that never go through onboarding — BUSINESS
  // sign-ups and company-created drivers — set immediately at creation).
  // Null means "not yet activated": the driver cannot go online, cannot
  // appear in a client's open-orders match, and cannot accept an order — all
  // three enforced server-side (task-07), not just the online toggle. A
  // stored timestamp rather than a derived read, mirroring how
  // `User.mustChangePassword` and `suspendedAt` are both stored rather than
  // computed live on every request.
  activatedAt DateTime?

  currentLat        Float?
  currentLng        Float?
  locationUpdatedAt DateTime?
  createdAt         DateTime  @default(now())
  updatedAt         DateTime  @updatedAt

  vehicles    Vehicle[]
  assignments DriverVehicleAssignment[]
  licence     DriverLicence?
  application DriverApplication?

  @@index([companyId])
}
```

### 9. Generate the migration, then hand-add the partial unique index

```
pnpm prisma migrate dev --name add_driver_onboarding
```

Requires a reachable `DATABASE_URL` (already required for local dev — no new env var).

After it generates, open the new `prisma/migrations/<timestamp>_add_driver_onboarding/migration.sql` and append (Prisma's schema language has no native partial-unique-index syntax, so this must be hand-written — same reason `vehicle_single_owner_check` lives in migration SQL instead of `schema.prisma`):

```sql
-- Exactly one live (non-superseded) document per application per document
-- type. A retake inserts a new row and sets supersededAt on the old one
-- instead of overwriting it, so the review history survives resubmission.
CREATE UNIQUE INDEX "driver_application_document_live_type_unique"
ON "DriverApplicationDocument" ("driverApplicationId", "type")
WHERE "supersededAt" IS NULL;
```

### 10. Backfill `activatedAt` for every existing `DriverProfile` row

`activatedAt` has no `@default`, so every pre-existing row gets `NULL` — which would silently deactivate every current driver, including `BUSINESS`-type and company-affiliated ones who never go through this wizard. Append this to the **same** migration file, after the `CREATE UNIQUE INDEX` above (and after Prisma's own `ALTER TABLE ... ADD COLUMN "activatedAt"` statement, which is already in the generated migration before your additions — do not move it):

```sql
-- Every driver that already existed before this feature shipped is
-- grandfathered as activated. Only new independent Individual/Individual
-- Entrepreneur sign-ups go through onboarding and start unactivated.
UPDATE "DriverProfile" SET "activatedAt" = now() WHERE "activatedAt" IS NULL;
```
