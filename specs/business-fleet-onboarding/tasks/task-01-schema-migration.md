# Task 01: Schema Migration — Company Fields, Vehicle Class, Business Application Models

## Status

pending

## Wave

1

## Description

A `LogisticsCompany` today is a six-field profile (name, VAT id, phone, one city, plus the FK to its `User`) with no registered address, no payout account, no contact person and no review lifecycle at all. This task adds every column and table the fleet onboarding feature needs: the company's legal, contact and payout details plus its cities of operation and an activation timestamp; a declared `vehicleClass` on `Vehicle`; the `BusinessApplication` / `BusinessApplicationVehicle` pair that carries the resumable draft, the company-level verdict and the per-vehicle verdicts; and the three enums those models key on. It also closes a long-documented race by adding the two partial unique indexes that make `DriverVehicleAssignment` exclusivity a database rule instead of a best-effort API check.

Everything here is additive and every new column is nullable or defaulted, because production already holds `LogisticsCompany`, `Vehicle` and `DriverVehicleAssignment` rows that predate this feature and must keep working untouched. Read the whole file before starting — several choices below (storing the vehicle class rather than deriving it, leaving `Vehicle.vehicleClass` deliberately un-backfilled, grandfathering existing companies as activated) are deliberate and explained inline. Do not "simplify" them.

## Technical Details

### 1. New fields on `LogisticsCompany`

All seven are nullable or list-typed. Existing rows were created by the internal admin's "add a seller" form, which collects none of these — a `String` (non-null) column would make the migration fail outright, and a non-null column with a placeholder default would put fabricated bank details on real companies.

```prisma
/// A fleet operator: its own login (role COMPANY), owns vehicles directly, and manages a
/// roster of drivers who fulfil the orders it dispatches to them. Phone is unique for the
/// same reason ClientProfile.phone is: it identifies one real business, one account.
/// The legal/contact/payout block below is collected by the fleet onboarding wizard
/// (`specs/business-fleet-onboarding`); every field in it is nullable because companies
/// created by the back office before that wizard existed have none of it.
model LogisticsCompany {
  id          String          @id @default(cuid())
  userId      String          @unique
  user        User            @relation(fields: [userId], references: [id], onDelete: Cascade)
  companyName String
  vatId       String
  phone       String          @unique
  /// The company's primary / registered city. Retained alongside
  /// `citiesOfOperation` — see the field's own comment.
  city        GeorgianCity

  /// Registered legal address as it appears on the company's registration.
  /// Free text: Georgian addresses are not structured consistently enough to
  /// normalise into street/number/postcode columns, and nothing queries on it.
  registeredAddress String?
  /// Payout account. Order revenue is settled here weekly, so it must belong to
  /// the registered entity — a rule an admin verifies during review, not one the
  /// schema can enforce. Stored as entered, minus spaces (the API normalises).
  bankAccountIban   String?
  /// The named person operations calls when an order needs a decision, their role
  /// in the company, and their email. Three plain columns rather than a
  /// `CompanyContact` model: there is exactly one contact per company in v1 (see
  /// requirements.md's "Multi-user company accounts" non-goal), and a 1:1 table
  /// would buy nothing but a join.
  contactName       String?
  contactRole       String?
  contactEmail      String?

  /// Every city this fleet picks up in. Orders outside these cities are not
  /// offered to the company's drivers. A Postgres enum array rather than a join
  /// table, following `DriverLicence.categories` — the list is short, always read
  /// whole, and never queried from the other side.
  citiesOfOperation GeorgianCity[]

  /// Set when an admin activates the fleet: the company is verified AND at least
  /// one of its vehicles is approved. Null means "cannot dispatch" — enforced
  /// server-side in task-21, not just hidden in the UI. A stored timestamp rather
  /// than a value derived from the application row on every request, mirroring
  /// `DriverProfile.activatedAt` and `User.suspendedAt`.
  activatedAt DateTime?

  drivers     DriverProfile[]
  vehicles    Vehicle[]
  orders      Order[]
  application BusinessApplication?
  createdAt   DateTime             @default(now())
  updatedAt   DateTime             @updatedAt
}
```

**Why `city` is retained rather than replaced by `citiesOfOperation`.** Four call sites read it today and none of them would work against an array: `GET`/`POST`/`PATCH /api/logistics-company` (`src/app/api/logistics-company/route.ts`) validates and writes it as a single `GeorgianCity`; `GET /api/admin/users/sellers` (`src/app/api/admin/users/sellers/route.ts:205`) projects `company.city` into a `city: GeorgianCity` response field shared with drivers; the admin sellers table renders it through `formatCity(seller.city)` (`src/app/admin/(sections)/users/sellers/page.tsx:289`); and `src/lib/company-dashboard-data.ts` types it as a scalar `GeorgianCity`. The two fields mean different things and both are wanted: `city` is where the business is registered and is what the back office lists a company under, `citiesOfOperation` is the dispatch catchment. Dropping `city` would be a breaking change to a public admin response shape for no gain, and the wizard simply writes both (the primary city is whichever the company enters first, per task-06). Do **not** add a NOT NULL constraint, a default, or any inference between the two.

**Backfilling `activatedAt` for existing companies.** `activatedAt` has no `@default`, so every pre-existing `LogisticsCompany` row gets `NULL` — which would silently lock every currently-dispatching company out of dispatch the moment task-21's gate ships. Grandfather them, exactly as the driver onboarding migration grandfathered `DriverProfile.activatedAt`. The `UPDATE` statement is in step 9 below, and it sets `activatedAt` to each row's own `createdAt` — not to `now()`, because the timestamp must not lie about when the company started operating.

**This backfill belongs to this migration and to no other.** task-21 (the dispatch gate) reads `activatedAt` and references this statement as already done; it must **not** propose a second migration to re-do it. One `UPDATE`, in this task's one migration file.

### 2. New `VehicleClass` enum and `Vehicle.vehicleClass`

```prisma
/// The five vehicle classes both onboarding wizards offer. A presentation-level
/// grouping over the `VehicleTypeSpec` catalogue — pricing and order matching
/// continue to key on `Vehicle.vehicleTypeSpecId` alone and never read this — but
/// stored, not derived, because it is what the company *declared* and what was
/// reviewed and approved. See `src/lib/driver-onboarding/vehicle-classes.ts` for
/// the (class, chassis type) -> spec code map; the licence category each class
/// requires lives there too, not here.
enum VehicleClass {
  SMALL_VAN
  LARGE_VAN
  MEDIUM_TRUCK
  HEAVY_FREIGHT_TRUCK
  TRAILER_TRUCK
}
```

On `Vehicle`, add one nullable field. Place it directly after `chassisType`, since the two are collected together and read together:

```prisma
model Vehicle {
  // ...existing fields unchanged...
  chassisType       ChassisType?
  /// The class the owner declared at onboarding, e.g. a 24 t articulated
  /// Trailer Truck. Nullable: every vehicle registered before this feature
  /// (the back office's "add a vehicle" form, the individual driver wizard's
  /// pre-existing rows) has none, and deriving one for them is exactly the
  /// operation this column exists to avoid. Consumers must treat `null` as
  /// "no declared class" and fall back to `vehicleTypeSpec.label`.
  vehicleClass      VehicleClass?
  payloadKg         Float?
  // ...rest unchanged...

  /// Singular, not a list, because `BusinessApplicationVehicle.vehicleId` is
  /// `@unique`: a vehicle appears in at most one business application review row
  /// for its lifetime. task-21's dispatch gate is written as
  /// `vehicle.applicationVehicle !== null && vehicle.applicationVehicle.status !== "APPROVED"`,
  /// which does not typecheck against an array.
  applicationVehicle BusinessApplicationVehicle?
}
```

**Why the class must be stored rather than derived from `(vehicleTypeSpecId, chassisType)`.** `src/app/api/driver-profile/onboarding/route.ts` currently *does* derive it, with a helper whose own doc comment concedes the weakness ("the same spec code could in principle be reachable from more than one class; the un-keyed scan is the fallback for a vehicle registered before `chassisType` was collected"). Four reasons that stops being acceptable at five classes:

1. **The inverse map is one ops decision away from being ambiguous.** Today's 8-cell map happens to be injective, but the seven locked cells are locked only because no spec backs them yet, and unlocking any of them breaks it. The obvious first candidate — `HEAVY_FREIGHT_TRUCK × REFRIGERATED` → `REFRIGERATED_TRUCK` — collides immediately with `MEDIUM_TRUCK × REFRIGERATED`, which already points at that same spec. The two heavy classes are the fragile pair in general: `HEAVY_FREIGHT_TRUCK` and `TRAILER_TRUCK` are both `HEAVY_DUTY`, both dry-box-only, and the payload band that separates them (10 t vs 24 t) is a pricing decision that `action-required.md` explicitly leaves open for ops sign-off. A derived class means every already-approved vehicle silently relabels itself the day that constant changes.
2. **The derivation's key is nullable.** `Vehicle.chassisType` is `ChassisType?`. Without it the inversion degrades to a scan on spec code alone, which is weaker still.
3. **It is a licence-gating input, not just a label.** The class carries the required licence category (Heavy Freight Truck = C, Trailer Truck = CE). Deriving it would make the category a driver was gated against a function of a mutable lookup table rather than of what the company declared and an admin approved.
4. **Three surfaces display it directly**, including for vehicles that have no verdict yet: the step-3 fleet table, the application status screen (task-15) and the admin detail drawer (task-20). The drawer in particular has to show the reviewer "the company says this is a Trailer Truck" as a reviewable claim, not a value the app computed for itself.

**`vehicleClass` is deliberately backfilled for nothing.** Leave every existing row `NULL`. Do not write an `UPDATE` for it. A backfill would have to run the inverse map — the exact operation the four points above declare unreliable — and would stamp a "declared" class onto vehicles whose owner never declared one and whose class nobody reviewed. `NULL` is the honest value and every consumer already has a spec-label fallback path.

### 3. New enums for the application lifecycle

Place all three next to the existing `DriverApplicationStatus` block, so the driver and business lifecycles read side by side.

```prisma
/// Lifecycle of one company's fleet onboarding application, deliberately
/// identical in shape to `DriverApplicationStatus`: `DRAFT` covers the whole
/// in-progress wizard, `PENDING` and `ACTION_REQUIRED` alternate as items are
/// flagged and corrected, and `APPROVED` is terminal (there is no "rejected,
/// reapply from scratch" state — see requirements.md's Assumptions). A company
/// has exactly one application for its lifetime; a flagged one is corrected and
/// resubmitted in place, never recreated.
enum BusinessApplicationStatus {
  DRAFT
  PENDING
  ACTION_REQUIRED
  APPROVED
}

/// The company-level verdict inside a business application, tracked separately
/// from the application's own `status` because the design reviews the company
/// once and each vehicle individually: the company can be VERIFIED while three
/// vehicles are still PENDING, and one vehicle can be FLAGGED without unpicking
/// the company's verdict. `FLAGGED` carries a reason in
/// `BusinessApplication.companyFlagReason`.
enum CompanyReviewStatus {
  PENDING
  VERIFIED
  FLAGGED
}

/// Per-vehicle review verdict within a business application. Mirrors
/// `DriverApplicationDocumentStatus` — same three values, same meaning: an
/// approved vehicle keeps its verdict across a resubmission, a flagged one is
/// the only kind the company can edit and resend.
enum BusinessApplicationVehicleStatus {
  PENDING
  APPROVED
  FLAGGED
}
```

### 4. New `BusinessApplication` model

1:1 on `LogisticsCompany`. `draft` carries the whole in-progress wizard as a versioned JSON blob so it is resumable across sessions and devices before anything is validated — the `Vehicle`, `DriverLicence` and `DriverVehicleAssignment` rows are written only at a successful submit (task-14), in one transaction, because `Vehicle.plateNumber` is globally `@unique` and an abandoned draft must never permanently claim a real plate. Place it directly after `LogisticsCompany` in the file.

```prisma
/// One fleet onboarding application per logistics company, 1:1 on
/// `LogisticsCompany`. `draft` holds the in-progress wizard (company details,
/// fleet composition counts, and one entry per vehicle carrying its
/// specification and its assigned driver) as
/// a versioned JSON blob — the exact shape is defined and narrowed in task-05 —
/// so nothing normalized is written until submit succeeds.
/// `reference` is the short human-readable code shown to the company and to the
/// admin reviewer (e.g. "BIZ-40219"); a bare `cuid` is not fit to read aloud in a
/// support call. It is NOT nullable: the row is only ever created by task-05's
/// lazy `GET`, which allocates the reference in the same `create` — never at
/// submit, and never as a nullable column filled in later.
/// `companyReviewStatus` is the company-level verdict and is
/// deliberately separate from `status`: the company is reviewed once, each
/// vehicle individually (see `BusinessApplicationVehicle`).
/// Admin review actions are recorded as `AuditLog` rows rather than a reviewer FK
/// on this model, matching every other admin mutation in this codebase.
model BusinessApplication {
  id        String           @id @default(cuid())
  companyId String           @unique
  company   LogisticsCompany @relation(fields: [companyId], references: [id], onDelete: Cascade)

  reference String                    @unique
  status    BusinessApplicationStatus @default(DRAFT)

  draft          Json?
  draftStep      Int       @default(1)
  draftUpdatedAt DateTime?

  companyReviewStatus CompanyReviewStatus @default(PENDING)
  /// Set only when `companyReviewStatus` is `FLAGGED`; cleared when the company
  /// resubmits. Exactly one of the four company-level flag reasons from the
  /// design — a CLOSED list, validated against those exact strings server-side.
  /// Free text is rejected; if operations needs an "Other" reason it is added to
  /// the list, not typed into this column.
  companyFlagReason   String?

  firstSubmittedAt DateTime?
  lastSubmittedAt  DateTime?
  submissionCount  Int       @default(0)

  vehicles  BusinessApplicationVehicle[]
  createdAt DateTime                     @default(now())
  updatedAt DateTime                     @updatedAt

  @@index([status])
}
```

Notes on specific choices, all of which mirror `DriverApplication`:

- `companyId` is `@unique` and cascades on company delete — one application per company for its lifetime, and deleting the company takes the application with it (unlike `DriverApplication.vehicleId`, which is `SetNull` precisely so retiring a vehicle never erases application history).
- `draftStep` defaults to `1`, not `0`; the wizard's steps are 1–5 and the step rail renders the number directly.
- `submissionCount` defaults to `0` and is incremented at every submit, so `firstSubmittedAt`/`lastSubmittedAt` plus the count tell a reviewer how many correction rounds a fleet has been through.
- `@@index([status])` backs the admin queue's status filter, which is the queue page's default read.
- There is no `activatedAt` here — activation lives on `LogisticsCompany.activatedAt`, because it is the *company* that can or cannot dispatch, and every gate in task-21 reads the company, not its application.

### 5. New `BusinessApplicationVehicle` model

One row per vehicle in the application, carrying that vehicle's review verdict. A join row rather than columns on `Vehicle` itself, because the verdict belongs to the *application round*, not to the vehicle: a company that is later re-reviewed gets new verdicts without rewriting the fleet, and a `Vehicle` that has never been through a business application carries no review columns at all. Place it directly after `BusinessApplication`.

```prisma
/// One reviewed vehicle inside a business fleet application. Rows are created at
/// submit time (task-14), in the same transaction that creates the `Vehicle`
/// rows themselves — never from a draft, since the vehicles do not exist until
/// then. `status` is the per-vehicle verdict the design shows on the status
/// screen and in the admin drawer: an `APPROVED` vehicle keeps its verdict
/// across a resubmission, and only a `FLAGGED` one is editable.
model BusinessApplicationVehicle {
  id                    String              @id @default(cuid())
  businessApplicationId String
  businessApplication   BusinessApplication @relation(fields: [businessApplicationId], references: [id], onDelete: Cascade)
  /// Nullable + SetNull: a company can remove a vehicle from its own fleet at any
  /// time through an existing, unrelated flow, and the review row must survive so
  /// the admin drawer can render "vehicle no longer on file" rather than vanishing
  /// a decided verdict. Mirrors `DriverApplication.vehicleId`.
  vehicleId             String?             @unique
  vehicle               Vehicle?            @relation(fields: [vehicleId], references: [id], onDelete: SetNull)

  /// Denormalised at submit so the admin queue, the drawer and the dispatch gate
  /// can read the declared class and body without a join that a null `vehicleId`
  /// would break. NOT NULL: unlike `Vehicle.vehicleClass` (which is nullable and
  /// deliberately un-backfilled for rows that predate this feature), every row
  /// here is created by task-14's submit from a draft that has both values.
  vehicleClass          VehicleClass
  chassisType           ChassisType

  status BusinessApplicationVehicleStatus @default(PENDING)
  /// Set only when `status` is `FLAGGED`; cleared when the vehicle is corrected
  /// and resubmitted. Exactly one of the six per-vehicle flag reasons from the
  /// design — a CLOSED list, validated against those exact strings server-side.
  /// Free text is rejected; if operations needs an "Other" reason it is added to
  /// the list, not typed into this column.
  flagReason String?
  /// When an admin last recorded a verdict on this row. Null while `PENDING`,
  /// stamped on approve/flag, and cleared back to null when the company corrects
  /// the vehicle through task-14's per-vehicle `PATCH`.
  decidedAt  DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([businessApplicationId])
}
```

- `vehicleId` is `String? @unique` with `onDelete: SetNull` — **not** required and **not** Cascade. A company can remove a vehicle from its own fleet at any time through an existing, unrelated flow. If the FK cascaded, that removal would silently delete a review row an admin had already decided; the drawer would show a fleet that had quietly shrunk with no trace of the verdict. With `SetNull` the row survives and the drawer renders "vehicle no longer on file" next to the verdict it still carries. This is exactly the reasoning `DriverApplication.vehicleId` already records, and this model follows it rather than inventing a second policy.
- **There is no compound `@@unique([businessApplicationId, vehicleId])`.** `vehicleId @unique` on its own is strictly stronger — a vehicle appears in at most one review row anywhere, not merely at most once per application — and it is what makes the submit endpoint's upsert-per-vehicle safe on a resubmission: it can `upsert` on `vehicleId` and preserve an existing `APPROVED` verdict instead of blindly creating a second row. A compound unique over a nullable column would additionally be useless in Postgres, which treats NULLs as distinct and so would permit unlimited orphaned rows per application.
- **There is no `position` column.** A vehicle's 1-based row number is derived by ordering on `createdAt` ascending and computing the index in the response. Any `orderBy: { position: ... }` anywhere in this feature is a bug — the number is presentational, it must not survive a re-order as stale data, and there is nothing that would keep a stored column dense after a `SetNull`.
- `vehicleClass` and `chassisType` are denormalised copies, NOT NULL, written by task-14's submit alongside the `Vehicle` row. They exist because `vehicleId` can go null: the queue, the drawer and task-21's dispatch gate all need the declared class and body, and a join through a null FK returns nothing. They are also what the company *declared and had reviewed*, which is the value the drawer must show even if the live `Vehicle` row is later edited.
- `@@index([businessApplicationId])` backs the detail read, which always loads an application's vehicles together.
- `onDelete: Cascade` is kept on the **application** side only: deleting the application drops its review rows, because a verdict outside an application means nothing.

### 6. Back-relations

`LogisticsCompany` needs `application BusinessApplication?` (included in the block in step 1). `Vehicle` needs `applicationVehicle BusinessApplicationVehicle?` (included in step 2) — **singular and optional, never a list**, because `BusinessApplicationVehicle.vehicleId` is `@unique`. Prisma will refuse to validate the schema without both — add them in the same edit, not as a follow-up.

The singular form is load-bearing downstream, not a stylistic preference: task-21's dispatch gate reads `vehicle.applicationVehicle !== null && vehicle.applicationVehicle.status !== "APPROVED"`, which does not typecheck against `BusinessApplicationVehicle[]`. If you find yourself writing `businessApplicationVehicles` anywhere, the `@unique` on `vehicleId` has been dropped by mistake.

### 7. Update the `DriverVehicleAssignment` doc comment

The model's comment currently ends:

```
/// A join table rather than a bare FK on `DriverProfile` so reassignment keeps
/// history: `unassignedAt` is set instead of the row being deleted. At most one row
/// per vehicle should have `unassignedAt: null` at a time — enforced at the API
/// layer, not by a DB constraint, matching how `Vehicle`'s single-owner rule is
/// partly enforced at the API layer too.
```

That last sentence stops being true in this migration. Replace it with:

```
/// A join table rather than a bare FK on `DriverProfile` so reassignment keeps
/// history: `unassignedAt` is set instead of the row being deleted. At most one
/// row per vehicle — and at most one per driver — has `unassignedAt: null` at a
/// time, enforced by two partial unique indexes added by hand in the migration
/// SQL (`driver_vehicle_assignment_live_vehicle_unique` and
/// `driver_vehicle_assignment_live_driver_unique`), since Prisma's schema
/// language has no partial-index syntax. The API layer still checks both rules
/// first, so callers get a readable error rather than a P2002 — the indexes are
/// what make the rule airtight under concurrency.
```

The route that documents the race is `src/app/api/logistics-company/vehicles/[id]/assignment/route.ts`; its in-file comment says the transaction "narrows the window rather than closing it; only a partial unique index on (`vehicleId`)/(`driverProfileId`) where `unassignedAt IS NULL` would make the rule airtight, and adding one is a schema change out of this route's scope." That is exactly what this migration adds. Do **not** edit that route in this task — task-07 owns the assignment API and will reconcile the comment and add P2002 handling there.

### 9. Hand-append the two partial unique indexes and the two backfills

Open the generated `prisma/migrations/<timestamp>_add_business_fleet_onboarding/migration.sql` and append the block below **at the end of the file**, after everything Prisma generated. Do not move or edit any generated statement. This is the same technique `driver_application_document_live_type_unique` already uses in `20260828101406_add_driver_onboarding/migration.sql` — Prisma's schema language cannot express a partial index, so it lives in migration SQL.

```sql
-- At most one live (non-closed) assignment per vehicle. Until now this was
-- enforced only inside the assignment route's transaction, which under
-- Postgres' default READ COMMITTED narrows the race window without closing it:
-- two concurrent assigns can each read "no live assignment" and both insert.
CREATE UNIQUE INDEX "driver_vehicle_assignment_live_vehicle_unique"
ON "DriverVehicleAssignment" ("vehicleId")
WHERE "unassignedAt" IS NULL;

-- The mirror rule: at most one live assignment per driver, so one person can
-- never be "currently driving" two vehicles and leave dispatch unable to tell
-- which. Same race, same fix.
CREATE UNIQUE INDEX "driver_vehicle_assignment_live_driver_unique"
ON "DriverVehicleAssignment" ("driverProfileId")
WHERE "unassignedAt" IS NULL;

-- Every logistics company that already existed before this feature shipped is
-- grandfathered as activated. `activatedAt` has no default, so without this
-- every currently-dispatching company would be locked out by task-21's gate the
-- moment it ships. Only companies that register through the new wizard start
-- unactivated. Mirrors the `DriverProfile.activatedAt` backfill in
-- 20260828101406_add_driver_onboarding.
--
-- `createdAt`, NOT `now()`: the column answers "since when has this company been
-- able to dispatch", and every one of these companies has been dispatching since
-- the day it was created. Stamping the migration's own clock would make every
-- grandfathered company look like it was activated the minute this feature
-- deployed — a timestamp that is wrong, that reads as a mass activation event in
-- any audit or cohort query, and that is unrecoverable once the real value is
-- overwritten. `createdAt` is non-null on every row, so this cannot leave a NULL.
UPDATE "LogisticsCompany" SET "activatedAt" = "createdAt" WHERE "activatedAt" IS NULL;

-- Prisma adds a scalar-list column without a DEFAULT, so pre-existing rows hold
-- a SQL NULL array. Prisma Client surfaces that as `[]`, but normalising it here
-- keeps raw SQL and any future direct reads honest. This is a data statement,
-- not a schema change, so it introduces no drift.
UPDATE "LogisticsCompany"
SET "citiesOfOperation" = ARRAY[]::"GeorgianCity"[]
WHERE "citiesOfOperation" IS NULL;
```

Do **not** additionally write `ALTER TABLE "LogisticsCompany" ALTER COLUMN "citiesOfOperation" SET DEFAULT ARRAY[]::"GeorgianCity"[]`. A default that does not exist in `schema.prisma` is reported as schema drift by the next `prisma migrate dev`, which would make every subsequent migration in this feature noisy. The `UPDATE` above is data-only and drift-free.

> **Warning — index creation fails against production if duplicates already exist.** `CREATE UNIQUE INDEX` is not tolerant: if the production `DriverVehicleAssignment` table already holds two live rows for the same `vehicleId` or the same `driverProfileId`, the statement aborts and the whole migration fails on deploy. That is a realistic outcome, not a theoretical one — the rule has until now been enforced only in application code, with the race documented in the route itself. `specs/business-fleet-onboarding/action-required.md` carries this as an explicit pre-deploy step; the duplicate-detection queries to run against production **before** `prisma migrate deploy` are:
>
> ```sql
> SELECT "vehicleId", count(*)
> FROM "DriverVehicleAssignment"
> WHERE "unassignedAt" IS NULL
> GROUP BY "vehicleId" HAVING count(*) > 1;
>
> SELECT "driverProfileId", count(*)
> FROM "DriverVehicleAssignment"
> WHERE "unassignedAt" IS NULL
> GROUP BY "driverProfileId" HAVING count(*) > 1;
> ```
>
> Resolve any rows those return (close the stale duplicate by stamping `unassignedAt`) before deploying. Do not "fix" this by making the indexes non-unique or by adding a deduplicating `UPDATE` to the migration — silently closing an assignment nobody reviewed is worse than a failed deploy, and which of two live assignments is the real one is an ops call.
