# Task 03: Vehicle type photo field, migration and taxonomy plumbing

## Status

complete

## Wave

1

## Description

The redesigned vehicles section of the homepage is photo-led: each `VehicleTypeSpec` in the catalogue is presented with a real photograph of that vehicle class rather than the two hand-drawn inline SVG glyphs the current section uses. `VehicleTypeSpec` has no image field today, so this task adds one — `imageUrl String?` — writes the migration, and carries the new field through the two hops between the database and the landing page: the public `GET /api/vehicle-types` response and the client-side taxonomy type in `src/components/landing/landing-vehicle-types.ts`.

**This is the only Prisma schema change in the entire `georgia-homepage-redesign` feature.** Everything else the redesign needs is content: `HomePageSection.type` and `.content` are free-form `String`/`Json` by design, and partner logos are `Banner` rows under a new placement key, not a new model. It is isolated into its own Wave 1 task so no other task in the feature ever edits `prisma/schema.prisma`, and so the migration lands and the Prisma Client regenerates before the Wave 2 tasks that compile against the new field start.

The field is **display-only**. Order matching and pricing key on `Vehicle.vehicleTypeSpecId` and `PricingRule` and must not learn about it.

## Technical Details

### Read these first

- `prisma/schema.prisma`, the `VehicleTypeSpec` model (**around line 344**) and the `VehicleCategory` enum (**around line 222**). The schema is heavily commented with `///` doc comments that explain *why* a field exists, not what it is — match that voice exactly. Two nearby comments are the tonal reference: `VehicleTypeSpec.cargoHeightM`'s "`0` means 'open / no height limit' … not a literal zero-height constraint", and the `ChassisType` enum's "Display and compliance-review only — it does not participate in order matching or pricing, both of which continue to key on `Vehicle.vehicleTypeSpecId` alone."
- `prisma/seed.ts` — 11 `VEHICLE_TYPE_SEEDS` entries and an idempotent `upsert` on `code` in `main()`.
- `src/app/api/vehicle-types/route.ts` — public, unauthenticated `GET` with an **explicit** `select` (ids and timestamps are withheld because the response is public).
- `src/components/landing/landing-vehicle-types.ts` — the client-side `LandingVehicleType` type and the module-level deduped fetch.

### Implementation Steps

1. **Add the field to `VehicleTypeSpec`.** Place `imageUrl` after `loadingAccessType` and before the `pricingRule` relation, so the scalar columns stay grouped ahead of the relations, matching how the model reads today:

   ```prisma
   /// Public Supabase Storage URL of a marketing photo for this vehicle class,
   /// set by a content manager from the back office (never by a driver, and
   /// never by the seed). It lives in the public `site-media` bucket, so the
   /// URL is directly renderable and no signed request is needed.
   ///
   /// Display-only, and deliberately so: order matching and pricing key on
   /// `Vehicle.vehicleTypeSpecId` and `PricingRule` alone and never read this.
   /// Nullable because no photography exists yet — the marketing page falls
   /// back to its inline vehicle glyphs for a type with no photo, so a null
   /// here is a normal, permanent-until-filled state rather than a gap to
   /// backfill.
   ///
   /// Not to be confused with `Vehicle.photoUrls`, which holds the photos a
   /// driver uploads of their own specific vehicle into the separate
   /// `vehicle-photos` bucket. This one is a picture of the *class*.
   imageUrl          String?
   ```

2. **Normalise and validate** before generating anything:

   ```bash
   pnpm exec prisma format
   pnpm exec prisma validate
   ```

3. **Generate and apply the migration.** The exact command:

   ```bash
   pnpm prisma migrate dev --name add_vehicle_type_photo
   ```

   This writes `prisma/migrations/<timestamp>_add_vehicle_type_photo/migration.sql` and regenerates the Prisma Client. The timestamped-prefix naming is what the CLI produces on its own and matches every existing folder — the most recent is `20260829121728_add_business_fleet_onboarding`. The generated SQL should be exactly one statement:

   ```sql
   -- AlterTable
   ALTER TABLE "VehicleTypeSpec" ADD COLUMN     "imageUrl" TEXT;
   ```

   Adding a nullable column is a non-destructive, non-blocking change: existing rows get `NULL` and nothing needs a default or a backfill. If the CLI proposes a reset, a data-loss warning, or any statement beyond that single `ALTER TABLE`, **stop** — something else has drifted, and this task is not the place to resolve it.

   If no dev database is reachable in the environment, run `pnpm exec prisma generate` instead so the Prisma Client types exist for typecheck, and say plainly in the final report that the migration still has to be generated and applied against the real database. Do not hand-write the migration folder to fake it.

4. **Carry the field through the public API.** In `src/app/api/vehicle-types/route.ts`, add `imageUrl: true` to the `select`, directly after `loadingAccessType: true`. Nothing else in that file changes: the `where: visibleVehicleTypeWhere()` gate, the `orderBy`, and the "no rate limit / public reference data" reasoning in its doc comment all stand. Exposing this on a public endpoint is intentional and safe — the value is already a public bucket URL rendered in an `<img>` on a page anyone can load.

5. **Widen the client taxonomy type.** In `src/components/landing/landing-vehicle-types.ts`, add to `LandingVehicleType`:

   ```ts
   /**
    * The vehicle-class photo a content manager set, or `null` when none has
    * been uploaded yet. Sections that show it fall back to a drawn glyph.
    */
   imageUrl: string | null;
   ```

   The type's existing header comment says the endpoint returns more per entry than the page uses and that anything unlisted is ignored — keep that comment accurate as you add the field. No change is needed to `loadVehicleTypes()` or `useLandingVehicleTypes()`: the response is cast, not validated, so a widened type is enough.

6. **Document the seed's deliberate silence.** `prisma/seed.ts` seeds no image URLs — there is no photography yet (see `action-required.md`). This is more than an omission, and the comment must say why:

   `main()` upserts with `update: { ...spec }`, spreading the whole seed object over the existing row. If `imageUrl` were added to `VehicleTypeSeed` as `imageUrl: null`, **every re-run of the seed would wipe every photo a content manager had set.** The field must therefore stay out of `VehicleTypeSeed` entirely, which leaves it untouched by the spread. Add a short comment to `VehicleTypeSeed` recording that:

   ```ts
   // `VehicleTypeSpec.imageUrl` is intentionally not part of this type. The
   // upsert below spreads a seed entry over the existing row, so a `null` here
   // would erase the marketing photo a content manager set every time the seed
   // was re-run. Photos are content, owned by the back office, not by the seed.
   ```

   Verify the seed still runs idempotently: `pnpm exec prisma db seed` should print `Seeded 11 vehicle type specs.` and leave any non-null `imageUrl` values in place.

7. **Verify.** `pnpm check` (which is `pnpm lint && pnpm typecheck`) must pass.

### Where the field is consumed

`/api/vehicle-types` is fetched **once per page load**, deduped at module level inside `landing-vehicle-types.ts`, and shared by five landing components that import `useLandingVehicleTypes` today:

- `src/components/landing/landing-hero.tsx`
- `src/components/landing/landing-ticker.tsx`
- `src/components/landing/landing-category-tiles.tsx`
- `src/components/landing/landing-vehicles.tsx`
- `src/components/landing/landing-quote-calculator.tsx`

Widening the shared type is therefore the only plumbing needed — none of those five components requires an edit in this task, and adding an optional field to the type breaks none of them. Several are rewritten in Wave 2 by other tasks; leave them alone here.

### Migration and codegen warnings

- **`prisma generate` runs on `postinstall` and inside `build`** (`"postinstall": "prisma generate"`, `"build": "prisma generate && next build"` in `package.json`). A teammate or CI that pulls this change gets the regenerated client automatically on install — but an already-running dev server holds the old client in memory. Restart `pnpm dev` after the migration or `imageUrl` will typecheck and still be `undefined` at runtime.
- Applying the migration to the real (Supabase-hosted) database is a deploy-time step, not something this task performs. Note it in the final report.

## Notes

- **The `site-media` bucket is created by hand.** `action-required.md` carries the step: Supabase dashboard → Storage → New bucket → `site-media`, **Public**. This task stores nothing and uploads nothing, so it is not blocked by that — but the URLs this column will eventually hold come from there, and a bucket created private will store fine and render broken. Buckets are never provisioned in code in this project.
- **`VehicleCategory` stays `MEDIUM_DUTY | HEAVY_DUTY`.** The design handoff groups vehicles into three families; the real taxonomy has two, and the design's nine placeholder vehicle types (Cargo Van / Extended Van / Crew Van / Truck 3t/5t/10t / Refrigerated / Flatbed / Crane) are flagged in the handoff itself as a placeholder set to be replaced by the real catalogue. Do not add an enum value, and do not rename one — the enum's declaration order is what `orderBy: [{ category: "asc" }, ...]` in the API route relies on to list medium-duty types first.
- **`visibleVehicleTypeWhere()` is unchanged.** `src/lib/vehicle-type-visibility.ts` withholds `TRAILER_TRUCK` from the public endpoint until the fleet holds a dispatchable one, so the homepage may render 10 types rather than 11. That is correct and deliberate; a missing photo slot for a hidden type is not a bug.
- **No `String @default("")`, no non-null column.** A nullable column is what makes "no photo yet" representable and lets the fallback glyph render. An empty string would be a second falsy state the rendering code would have to test for separately.
- The 11 seeded codes, for reference when task-13's admin list is built later: `MINIVAN`, `MPV`, `CARGO_VAN`, `CLOSED_BOX_VAN`, `REFRIGERATED_VAN` (medium-duty); `BOX_TRUCK`, `FLATBED_TRUCK`, `CURTAINSIDER_TRUCK`, `REFRIGERATED_TRUCK`, `LARGE_FREIGHT_TRUCK`, `TRAILER_TRUCK` (heavy-duty). The target photo size agreed in planning is 720×560.
