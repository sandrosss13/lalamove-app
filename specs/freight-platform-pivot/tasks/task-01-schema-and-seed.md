# Task 01: New Prisma schema, migration & seed data

## Status

done

## Wave

1

## Description

This is the foundation task for pivoting the app from small-parcel delivery to commercial freight/
cargo logistics. It replaces the `PackageType` enum and the flat `VehicleType` enum with a new,
database-backed vehicle taxonomy (`VehicleTypeSpec` + `PricingRule`) and cargo taxonomy
(`CargoCategory`), adds a `LogisticsCompany` account type, and reshapes `Vehicle`/`Order`/
`DriverProfile` to support both independent drivers (own their own vehicle, as today) and companies
(own a fleet, dispatch internally to their drivers). Every other task in this spec depends on this
one — nothing else can be coded against the new model until it exists.

## Technical Details

### Schema changes

Replace the current `PackageType` enum entirely (delete it) and the current `VehicleType` enum
entirely (delete it — every value it holds, e.g. `FLATBED`, `PICKUP`, `VENDING_TRUCK`,
`ICE_CREAM_TRUCK`, etc., is gone; nothing references it after this task lands). Add:

```prisma
enum UserRole {
  CLIENT
  DRIVER
  COMPANY
}
```

(This is the existing `UserRole` enum — just add the `COMPANY` value alongside `CLIENT`/`DRIVER`.
Also update the Better Auth `role` additional-field comment in `src/lib/auth.ts` if it enumerates
role values — check that file, but do not otherwise touch its logic; that's out of scope for this
task, task-03 owns wiring `COMPANY` through sign-up.)

```prisma
enum VehicleCategory {
  MEDIUM_DUTY
  HEAVY_DUTY
}

enum LoadingAccessType {
  REAR_DOOR
  SIDE_DOOR
  RAMP
  TAIL_LIFT
  OPEN_FLATBED
}

enum CargoCategory {
  FURNITURE_FURNISHINGS
  APPLIANCES
  RETAIL_STOCK
  EVENT_EQUIPMENT
  FULL_RELOCATION
  INDUSTRIAL_SUPPLIES
  CONSTRUCTION_MATERIALS
}

/// A vehicle "make/model class" the platform supports — e.g. "Box Truck". Specs and
/// pricing are data (seeded), not hardcoded UI constants, so they can be tuned without
/// a code change. `code` is the stable identifier other tables and UI option lists key on.
model VehicleTypeSpec {
  id                String            @id @default(cuid())
  code              String            @unique
  label             String
  category          VehicleCategory
  maxPayloadKg      Float
  cargoLengthM      Float
  cargoWidthM       Float
  cargoHeightM      Float
  loadingAccessType LoadingAccessType
  pricingRule       PricingRule?
  vehicles          Vehicle[]
  orders            Order[]
  createdAt         DateTime          @default(now())
  updatedAt         DateTime          @updatedAt
}

/// One pricing rule per vehicle type. `freeLoadingMinutes` is the buffer before
/// `overtimeRatePerMinute` kicks in; `minimumFare` is a floor applied after all other
/// components are summed.
model PricingRule {
  id                    String          @id @default(cuid())
  vehicleTypeSpecId     String          @unique
  vehicleTypeSpec       VehicleTypeSpec @relation(fields: [vehicleTypeSpecId], references: [id], onDelete: Cascade)
  baseFare              Float
  pricePerKm            Float
  pricePerMinute        Float
  freeLoadingMinutes    Int
  overtimeRatePerMinute Float
  helperFee             Float
  minimumFare           Float
  createdAt             DateTime        @default(now())
  updatedAt             DateTime        @updatedAt
}

/// A fleet operator: its own login (role COMPANY), owns vehicles directly, and manages a
/// roster of drivers who fulfil the orders it dispatches to them. Phone is unique for the
/// same reason ClientProfile.phone is: it identifies one real business, one account.
model LogisticsCompany {
  id          String          @id @default(cuid())
  userId      String          @unique
  user        User            @relation(fields: [userId], references: [id], onDelete: Cascade)
  companyName String
  vatId       String
  phone       String          @unique
  city        GeorgianCity
  drivers     DriverProfile[]
  vehicles    Vehicle[]
  orders      Order[]
  createdAt   DateTime        @default(now())
  updatedAt   DateTime        @updatedAt
}
```

Modify `DriverProfile`:
- Remove the `vehicleType VehicleType?` field entirely (it was already unused/vestigial before this
  pivot — confirmed not referenced in sign-up or any API route — and its type no longer exists).
- Add `companyId String?` and `company LogisticsCompany? @relation(fields: [companyId], references: [id], onDelete: SetNull)`.
  `SetNull` (not `Cascade`) so a driver removed from a company keeps their account, just becomes
  independent again.
- Everything else on `DriverProfile` (`isOnline`, `city`, `accountType`, name/company/vat fields,
  `phone`, `currentLat`/`currentLng`/`locationUpdatedAt`) stays as-is.

Modify `Vehicle` — ownership becomes either an independent driver OR a company, never both, never
neither:
```prisma
model Vehicle {
  id                String            @id @default(cuid())
  driverProfileId   String?
  driverProfile     DriverProfile?    @relation(fields: [driverProfileId], references: [id], onDelete: Cascade)
  companyId         String?
  company           LogisticsCompany? @relation(fields: [companyId], references: [id], onDelete: Cascade)
  vehicleTypeSpecId String
  vehicleTypeSpec   VehicleTypeSpec   @relation(fields: [vehicleTypeSpecId], references: [id])
  plateNumber       String            @unique
  make              String
  model             String
  year              Int
  photoUrls         String[]
  orders            Order[]
  createdAt         DateTime          @default(now())
  updatedAt         DateTime          @updatedAt

  @@index([driverProfileId])
  @@index([companyId])
}
```
(This drops the old `capacityKg` field — capacity now comes from `vehicleTypeSpec.maxPayloadKg`,
so it would be redundant.) After generating the migration, hand-edit the generated `migration.sql`
to add a `CHECK` constraint enforcing "exactly one of driverProfileId/companyId is set" — Prisma's
schema language has no native XOR, so add this manually to the SQL file before applying it:
```sql
ALTER TABLE "Vehicle" ADD CONSTRAINT "vehicle_single_owner_check"
  CHECK (
    ("driverProfileId" IS NOT NULL AND "companyId" IS NULL) OR
    ("driverProfileId" IS NULL AND "companyId" IS NOT NULL)
  );
```
Also enforce this at the application level wherever a `Vehicle` is created (task-04's concern) —
the DB constraint is a backstop, not a substitute for a clear API error message.

Modify `Order`:
```prisma
enum OrderStatus {
  PENDING
  CLAIMED
  ACCEPTED
  IN_TRANSIT
  COMPLETED
  CANCELLED
}

model Order {
  id                String            @id @default(cuid())
  cargoCategory     CargoCategory
  description       String?
  requiresHelper    Boolean           @default(false)

  pickupAddress     String
  pickupLat         Float?
  pickupLng         Float?
  dropoffAddress    String
  dropoffLat        Float?
  dropoffLng        Float?

  distanceKm        Float
  baseFare          Float
  distanceFare      Float
  timeFare          Float
  helperFee         Float             @default(0)
  overtimeFee       Float             @default(0)
  price             Float

  vehicleTypeSpecId String
  vehicleTypeSpec   VehicleTypeSpec   @relation(fields: [vehicleTypeSpecId], references: [id])

  status            OrderStatus       @default(PENDING)

  clientId          String
  client            User              @relation("ClientOrders", fields: [clientId], references: [id], onDelete: Cascade)

  companyId         String?
  company           LogisticsCompany? @relation(fields: [companyId], references: [id], onDelete: SetNull)

  driverId          String?
  driver            User?             @relation("DriverDeliveries", fields: [driverId], references: [id], onDelete: SetNull)

  vehicleId         String?
  vehicle           Vehicle?          @relation(fields: [vehicleId], references: [id], onDelete: SetNull)

  inTransitAt       DateTime?
  completedAt       DateTime?
  waitingMinutes     Int?

  createdAt         DateTime          @default(now())
  updatedAt         DateTime          @updatedAt

  @@index([clientId])
  @@index([driverId])
  @@index([companyId])
  @@index([vehicleId])
  @@index([status])
}
```
Notes on the new `OrderStatus.CLAIMED`: an order moves `PENDING` → `CLAIMED` when a
`LogisticsCompany` claims it (sets `companyId`, `driverId`/`vehicleId` still null), then `CLAIMED` →
`ACCEPTED` when the company dispatches it to one of its own drivers (`driverId`/`vehicleId` now
set). An independent driver skips the `CLAIMED` state entirely and goes straight `PENDING` →
`ACCEPTED` (this is task-07's concern; this task only needs the schema to support both paths).

`price` is the up-front quoted total (`baseFare + distanceFare + timeFare + helperFee`, floored at
`minimumFare`); `overtimeFee` is added on top at completion time and is not part of the up-front
quote (task-07's concern).

### Implementation steps

1. Edit `prisma/schema.prisma` with all the changes above.
2. Because `Order` and `Vehicle` change shape incompatibly (enums removed, required fields added),
   truncate their existing rows before generating the migration so the migration doesn't fail
   against existing data: connect to the dev database and run
   `TRUNCATE TABLE "Order", "Vehicle" RESTART IDENTITY CASCADE;` (via
   `pnpm exec prisma db execute --stdin` or equivalent) **before** running `migrate dev`. Do not
   truncate `User`, `Session`, `Account`, `Verification`, `ClientProfile`, or `DriverProfile` — only
   `Order` and `Vehicle` have breaking shape changes. This was explicitly confirmed as acceptable
   during planning (dev/pre-launch data only) — see `action-required.md`.
3. Run `pnpm exec prisma migrate dev --name freight_platform_pivot`. Review the generated SQL and
   add the `CHECK` constraint from above before/after generation as needed (you can edit the
   generated `migration.sql` file directly before it's applied, or apply a follow-up migration for
   just the constraint — either is fine, whichever is simpler with the Prisma CLI's flow).
4. Write `prisma/seed.ts` seeding the `VehicleTypeSpec` + `PricingRule` rows from the table below,
   using `prisma.vehicleTypeSpec.upsert(...)` keyed on `code` so the seed is idempotent (safe to
   re-run). Wire `pnpm exec prisma db seed` to work (add the `"prisma": {"seed": "..."}` block to
   `package.json` if not already present).
5. Run the seed and confirm all 10 rows exist with their pricing rules attached.

## Acceptance Criteria

- [ ] `PackageType` and the old `VehicleType` enum no longer exist anywhere in `prisma/schema.prisma`.
- [ ] `VehicleTypeSpec`, `PricingRule`, and `LogisticsCompany` models exist with the fields above.

- [ ] `Vehicle` has both `driverProfileId` and `companyId` as optional, a `vehicleTypeSpecId`

      (`baseFare`/`distanceFare`/`timeFare`/`helperFee`/`overtimeFee`/`price`), `vehicleTypeSpecId`,
      `companyId`, `inTransitAt`/`completedAt`/`waitingMinutes`, and `OrderStatus` includes `CLAIMED`.
- [ ] `pnpm exec prisma migrate status` reports the schema in sync with the dev database.
- [ ] `pnpm exec prisma db seed` (or equivalent) populates exactly 10 `VehicleTypeSpec` rows, each
      with exactly one `PricingRule`, matching the table above.

      migration steps); `User`/`Session`/`ClientProfile`/`DriverProfile` rows are untouched.
